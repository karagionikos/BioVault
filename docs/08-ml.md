# 08 · Machine learning

Three pieces, in the order they arrive:

1. **SPECTER2 fingerprints** — the "reader" that turns text into vectors (P1).
2. **The hand-tuned "related" score** — combines fingerprints with shared details (P1), and logs every decision.
3. **Your own link model** — built from scratch, trained on your decisions, replaces the hand-tuned score once it proves better (P3) (D66, D70).

Plus, optionally, the **bring-your-own-model connector** for generative features (P3) (D48).

## 1 · SPECTER2 on both devices (D52, D61, D71)

**Model:** SPECTER2 (AllenAI) — BERT-base-sized, trained on ~6M citation triplets across 23 fields, input = title + abstract, English, Apache-2.0. Base `allenai/specter2_base` + adapters:
- **proximity** adapter (`allenai/specter2`) — for papers and paper-like text;
- **adhoc query** adapter (`allenai/specter2_adhoc_query`) — for short search queries.

**What gets fingerprinted** (my call; validate with the evaluation set below):

| Item | Text | Variant |
|---|---|---|
| Paper | `title [SEP] abstract` | proximity |
| Finding | `key_result [SEP] takeaway + notes` | proximity |
| Lead | claim text | proximity |
| Vault search query | the query | adhoc query |

Sketches are never fingerprinted (D67).

**When:** a paper is fingerprinted in the background right after saving (on whichever device saved it); a finding is re-fingerprinted a few seconds after you stop editing it (debounced). The prompt never waits for this — it uses what's ready.

**On-device pipeline:**
1. Tokenize with the model's WordPiece tokenizer (Rust `tokenizers` crate), max 512 tokens.
2. Run the ONNX model (8-bit quantized) in the core; take the first-token ([CLS]) output → 768 floats; L2-normalize.
3. Store in `fingerprint` keyed by `(node, model_id, variant, content_hash)`; recompute only when the text's hash changes.

**Preparing the model (one-time, in `ml/`):** load base + adapter in Python, merge/activate the adapter, export to ONNX, apply dynamic int8 quantization, verify that the quantized outputs match the original closely (cosine ≥ 0.99 on a sample), record checksums. Expect roughly 100–150 MB per variant after quantization; if two variants are too heavy for the phone, v1 can use proximity for queries too (Spike 0 decides).

**Rules:** both devices must run the **identical** model files (F20). Switching models = re-fingerprint the whole vault (minutes at this scale) via a `model_registry` op that both devices follow.

## 2 · The v1 "related" score (D39)

For a source item (the paper or finding being processed), candidates = all live papers/findings/leads except itself, findings of the same paper, already-linked items, and Trash.

```
score = 0.60·sim + 0.15·cat + 0.10·topic + 0.10·cite + 0.05·author
```

| Feature | Definition (0–1) |
|---|---|
| sim | cosine similarity of fingerprints, rescaled to its percentile within your vault |
| cat | 1 = share a category at depth ≥2; 0.5 = share only a top-level category; 0 otherwise |
| topic | Jaccard overlap of OpenAlex topics ∪ MeSH major headings |
| cite | 1 = one cites the other; 0.5 = share ≥3 references (OpenAlex); 0 otherwise |
| author | 1 = share an author |

Weights are **starting values** — tune them by watching the acceptance rate in Stats. Show the top 5 with a one-line "why" built from the strongest features ("similar meaning · cites it · same category: BDNF").

## 3 · Decision logging — from day one (D66)

Every suggestion shown writes a `suggestion_event` ([03](03-data-model.md#suggestion-event-d66--append-only)) with:
- the **feature snapshot at that moment**, the score, the scorer version, its rank;
- your decision: **linked (with type)**, **dismissed**, or **ignored** (prompt closed without action).

Links you create manually are positive examples too. Nothing here leaves your devices.

**Developer export (my call):** Settings → Developer → *Export training data* writes `links.csv`, `suggestion_events.csv` and `features.parquet` for the `ml/` notebooks.

## 4 · Your own link model (P3, D66, D70)

> **Human-owned** — designing features and judging the evaluation are the learning goal.

**Task:** given a source item, rank candidates by how likely *you* are to link them. It learns *whether* two items connect, not *how* (link type stays yours, D66).

**Labels**
- Positive: links you created; suggestions you linked.
- Negative: suggestions you dismissed.
- Weak negative (lower weight): shown and ignored; random unlinked pairs from the vault.

**Features** (start with v1's, then add):
- fingerprint similarity (paper↔paper, finding↔finding, cross);
- category tree distance; topic/MeSH overlap; citation, co-citation, bibliographic coupling;
- year gap, same journal, study-type pair, species pair;
- **graph features from your own links:** shared neighbors, Adamic–Adar index, degree of each node.

**Models to try:** logistic regression (baseline) → gradient-boosted trees → small neural network (PyTorch). Export to ONNX (`skl2onnx` / `onnxmltools` / `torch.onnx`); check licenses are MIT/Apache.

**When to start:** at roughly **200 links and 300 logged decisions** (my call) — likely by the time P3 reaches it.

**Evaluation protocol**
- **Time-based split:** train on older decisions, test on the newest ~20% (no peeking into the future).
- Metrics on the test set: precision@5, recall@10, mean reciprocal rank — the same numbers computed for the v1 hand-tuned score on the same split.
- **Replace v1 only if** the model is better on at least two metrics and not clearly worse on any (D75).

**Deployment**
- Export → *Settings → Developer → Install model* on the desktop → `model_registry` op → the file syncs to the phone as a blob → both devices switch when verified. `scorer_version` on every event keeps history interpretable.
- Retrain manually whenever you like; old models are kept so you can roll back.

**Optional later exercise:** re-implement training (e.g. logistic regression or a small network with gradient descent) by hand in Rust (D70).

## 5 · Bring-your-own-model connector (P3, D40, D43, D48)

- **One setting:** OpenAI-compatible endpoint (server address, API key, model name) + "Test connection". Works with local runners (Ollama, LM Studio) on your own PC, or any provider that speaks the same API with your key.
- **All AI features off by default;** each is a separate toggle; the app works fully without any of them.
- Candidate features: sample size / population / intervention / outcome extraction (fills `label_sample_size`, marked "extracted by model"); draft a finding's **key result** for you to edit; suggest a link type between two findings; later, ask questions across your vault.
- **Hard rule, enforced in the core (D41):** model output can never be written into a `takeaway` block; any AI-written block carries `ai_generated = true` and is visibly marked.

## Evaluation set for the reader (my call)
Before relying on suggestions, build a small benchmark: ~50 of your own papers where you already know which ones connect. Use it to check (a) which text recipe above works best for findings, (b) whether 8-bit quantization hurt quality, and (c) later, how your link model compares. It doubles as a regression test whenever a model changes.
